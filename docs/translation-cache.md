# Translation-cache comparisons

`TTT_TCG_CACHE_MIB` controls QEMU's translated-code cache. It is separate from
guest RAM, graphics caches and the container memory limit. The current default
is 1024 MiB. QEMU documents the underlying `tb-size` option in
[its invocation reference](https://www.qemu.org/docs/master/system/invocation.html).

A smaller limit is a candidate for reducing emulator memory, not a measured
whole-browser saving. More frequent cache flushes can require code to be
translated again. Compare memory, CPU consumption, cold startup and page
execution before adopting a smaller value. A completed boot alone is not a
browser performance check.

## Isolate the renderer cache

Stop the guest cleanly before preparing a baseline. Preserve its original disk
and renderer cache outside the checkout. For a comparison, make one baseline
cache copy and give each trial a fresh copy of that same baseline. Keep all
copies private; renderer caches contain derived application data.

The following commands assume that the guest is stopped, the parent directory
exists, and `TTT_VM_DIR` identifies its prepared bundle:

```sh
export TTT_CACHE_BASE=/absolute/path/to/private/cache-baseline
mkdir -m 700 "$TTT_CACHE_BASE"
cp -a --reflink=auto -- "${TTT_VM_DIR:?Set the stopped VM directory}/cache/." \
  "$TTT_CACHE_BASE/"

export TTT_CACHE_DIR=/absolute/path/to/private/cache-trial-001
mkdir -m 700 "$TTT_CACHE_DIR"
cp -a --reflink=auto -- "$TTT_CACHE_BASE/." "$TTT_CACHE_DIR/"
```

The exclusive `mkdir` calls intentionally reject existing output directories.
Keep the baseline unchanged and choose a new trial path for each run. Verify
the complete relative filename set and each file's hash before starting; after
shutdown, check that the baseline and original cache have neither changed
entries nor gained new ones. Comparing only previously recorded hashes misses
new cache files.

Compose mounts `TTT_CACHE_DIR` at `/root/.cache`. When the variable is unset or
empty, the existing `$TTT_VM_DIR/cache` location remains the default. This
override changes only the host cache mount; it does not reset Safari's saved
tabs, cookies or other guest disk state. The container must be able to read and
write the chosen directory under the same ownership rules as the VM bundle.

Use the same full Compose file list as your existing deployment, including its
proxy overlay when applicable. Inspect `docker compose config` before creating
the container and its actual Docker mounts afterward: `/root/.cache` must have
exactly one source, pointing to that trial's directory. Avoid a second overlay
that replaces it with the original path.

Some renderer components use `/root/.cache` even when `XDG_CACHE_HOME` or
`MESA_SHADER_CACHE_DIR` points elsewhere. Redirecting those environment variables
alone did not isolate all cache writes in a native trial. If your existing
configuration explicitly sets them, keep them inside the same trial mount or
record and isolate their separate locations as well.

## Measure the whole workload

Change `TTT_TCG_CACHE_MIB` only between clean guest lifetimes. Keep the QEMU
binary, guest CPU/RAM settings, native display geometry, renderer, service
profile, clock policy, container limits, starting guest disk state and proxy
route fixed. Cache isolation does not make a guest boot a saved-state resume.

For each trial:

1. Retain the original `launch.json`, including host boot identity and cache
   setting. Verify the effective QEMU configuration separately.
2. Start `sample_resources.py --host-memory` as the container starts, using
   the same duration for both sides. Record native Safari foreground time
   separately from successful page rendering.
3. Open the same local diagnostic once at the same scheduled boot offset.
   Check native screenshots, canvas, WebGL, workers and calibrated touch.
   Preserve a failed request instead of repeating it to obtain a passing run.
4. Check the intended proxy before external browsing. Run the same page
   workload, with its own fixed resource window and native content checks.
   Verify the route again afterward; changing external responses remain a
   limitation even when the exit IP is unchanged.
5. After each resource window, optionally record QEMU's read-only `info jit`
   output and the query duration. Keep it out of the timed window. Record
   buffer capacity, generated bytes, translation-block flushes and invalidations.
   These counters belong to one QEMU lifetime; compare deltas over equivalent
   phases, not unrelated absolute totals.
6. Stop through the native shutdown path, verify that termination was not
   forced, and check the original disks and cache manifests before the next run.

`info jit` is a diagnostic from the pinned QEMU build, not a stable SDK schema.
Its generated-byte count is current cache use; its flush count is cumulative.
Neither identifies the reason for every flush or proves a specific CPU cost.
Use whole-container CPU and wall time to assess that cost. Do not run a large
JIT dump or a CPU profiler in the performance window; use a separate
[profiling run](cpu-profiling.md) when attribution is needed.

Record whether the host was rebooted between trials. Host page-cache warmth,
memory accounting and run order still affect results even with identical guest
and renderer-cache files. Use a repeat control before attributing small
differences to the cache setting. A peak pinned at the container limit, memory
pressure, worker timeouts or missing page content can invalidate a proposed
smaller profile even when there are no OOM kills.

## Initial native comparison

Two sequential cold guest starts used the same preserved device image, exact
4,559-file renderer-cache seed, two application CPUs, 2 GiB guest RAM, native
1179 × 2556 display, one lavapipe thread and four-CPU/6.5-GiB container limits.
The 512-MiB trial ran first after a host reboot; the 1024-MiB control used the
same host without another reboot. Both retained the original 600-second
startup measurement and sent the Safari launch request once.

| Startup observation | 512 MiB | 1024 MiB |
| --- | ---: | ---: |
| Safari foreground verified | No | 259.4 s |
| Original readiness result | Launch reply timed out at 328.6 s | Complete at 259.5 s |
| Container peak over the 600-second window | 6.408 GiB | 5.907 GiB |
| Average host CPU cores used | 2.343 | 2.243 |
| Translation-block flushes after the window | 39 | 9 |
| Memory-limit events / OOM kills | 0 / 0 | 0 / 0 |

The 512-MiB failure capture showed Home with graphics artifacts. Its local
navigation, touch and external-page steps were not requested after the failed
readiness gate. The 1024-MiB control passed local canvas, WebGL and both worker
checks; its diagnostic callback took 63.1 seconds after navigation. Its one
calibrated tap passed the four property-reading paths. The tap was requested
at 523.7 seconds after boot, later than its scheduled 500-second offset because
the visual-review gate had not yet been recorded.

These windows contain different completed workloads, and host cache warmth
and run order were not controlled. The memory and CPU figures therefore do
not isolate a cache-size effect or establish a general performance percentage.
Flush counts alone do not explain the launch failure. This pair nevertheless
provides no qualified smaller-cache configuration: retain the 1024-MiB default.
